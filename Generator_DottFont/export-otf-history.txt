ÉTAPE 3 — TENTATIVES DE CORRECTION DE BASELINE_Y
------------------------------------------------------------

Le problème central : trouver la position Y (en pixels canvas) du baseline
alphabétique quand le texte est rendu avec textBaseline='top' à y=PADDING.

renderTextMask() dessine ainsi :
  ctx.textBaseline = 'top';
  ctx.fillText(text, PADDING, PADDING);  // PADDING = 30px, FONT_SIZE = 150px

TENTATIVE A — fontBoundingBoxAscent avec textBaseline='alphabetic' (code initial)
  BASELINE_Y = PADDING + fontBoundingBoxAscent('H', textBaseline='alphabetic')
  Résultat : glyphes +211 unités au-dessus du baseline (BBox bottom = 211)
  Raison de l'échec : fontBoundingBoxAscent retourne l'ascender du font entier
  (~1050/1024 * 150 ≈ 153px), pas la distance entre le point 'top' et le baseline réel.

TENTATIVE B — alphabeticBaseline avec textBaseline='top'
  BASELINE_Y = PADDING + alphabeticBaseline('H', textBaseline='top')
  Résultat : glyphes décalés dans les valeurs négatives (en dessous du baseline)
  Testé sur Chrome ET Firefox avec le même résultat.
  Raison de l'échec : la spec Canvas utilise la convention "positif = vers le haut".
  Avec textBaseline='top', le baseline est EN DESSOUS du point de référence,
  donc alphabeticBaseline retourne une valeur NÉGATIVE dans Chrome/Firefox.
  → BASELINE_Y = PADDING + (valeur négative) = trop petit → glyphes trop bas.

TENTATIVE C — actualBoundingBoxDescent de 'A' avec textBaseline='top' (VALIDÉE)
  BASELINE_Y = PADDING + actualBoundingBoxDescent('A', textBaseline='top')
  Principe : 'A' a yMin=0 (touche exactement le baseline alphabétique).
  Sa descente depuis le point 'top' = distance de 'top' au baseline.
  actualBoundingBoxDescent est toujours positif (convention CSS, downward positive).
  → Valeur cross-browser stable.
  Résultat : CORRECT — alignement baseline validé

ÉTAPE 4 — TREMBLING (tremblement dans l'OTF exporté)
------------------------------------------------------------
Constaté : comparaison 04-07_test06 vs rendu navigateur → points perdent leur
alignement dans l'OTF, comme un tremblement colonne par colonne.

HYPOTHÈSE A — rounding flottant sur fx/fy (Math.round)
  Ajout de Math.round() sur fx et fy dans export-otf.js.
  Test07 : tremblement toujours présent → hypothèse incorrecte.

HYPOTHÈSE B — gradient normalisé à la largeur de chaque caractère (VALIDÉE)
  Cause racine : drawMeshGradientPreview() normalisait l'axe X du gradient
  sur canvasW (largeur variable par caractère). Chaque caractère avait donc
  une couleur de dot différente selon sa propre largeur → taille de dot variable
  colonne par colonne → apparence de "tremblement".

  Fix : ajout d'un paramètre refWidth à drawMeshGradientPreview().
  Lors de l'export OTF, on passe canvasH (constante = FONT_SIZE + 2*PADDING)
  comme référence fixe pour tous les caractères :
    drawMeshGradientPreview(canvasW, canvasH, undefined, canvasH)
  → le gradient est identique pour tous les caractères → dots cohérents.

------------------------------------------------------------
Ajout d'un bouton PNG dans index.html + export-png-btn stylisé comme export-otf-btn.

Fonctionnement dans script-generator_DottFont.js :
  - Sérialise le SVG #output via XMLSerializer
  - Crée un Blob URL → charge dans un <img>
  - Dessine sur un <canvas> à résolution 4× (scale fixe)
  - Télécharge via canvas.toDataURL('image/png')
  Filename : {shape}_{tailleGen}_{size}_{presence}.png

Pourquoi SVG → canvas → PNG (et pas canvas direct) :

  Le facteur 4× est fixe pour garantir une qualité constante.

ÉTAPE 10 — UNION BOOLÉENNE DES CONTOURS (Path > Union)
------------------------------------------------------------
Problème : chaque dot = 1 contour indépendant dans l'OTF.
Les contours se chevauchent, ce qui peut poser problème
dans certains renderers (PDF, imposition, logiciels de signe).

Objectif : fusionner tous les dots d'un glyphe en une seule
silhouette unifiée — équivalent de Path > Union dans Inkscape.

Solution : Clipper.js (port JS du moteur Clipper, union booléenne
de polygones), chargé dynamiquement depuis CDN sans modifier index.html.

Approche :
  - Les fonctions addXxxToPath (Bézier) sont remplacées par des
    fonctions getXxxPolygon retournant des tableaux de points {X, Y}
    (format Clipper, coordonnées en entiers via CLIPPER_SCALE = 100).
  - Les courbes sont approximées en polygones :
      circle        → 32 points (sub-pixel à toutes tailles)
      square        → 4 points (exact)
      ellipse       → 32 points
      trait         → 16 points par demi-cercle + segments droits
      circle_outline→ 32 points outer (CCW) + 32 points inner (CW = trou)
  - Après la boucle de génération, Clipper effectue l'union (ctUnion,
    pftNonZero) sur tous les polygones du glyphe.
  - Le résultat est converti en opentype.Path (moveTo / lineTo / close).

Winding :
  Toutes les formes solides sont générées en CCW (winding +1 en Y-up).
  Le polygone inner de circle_outline est généré en CW (winding -1)
  pour créer un trou. La règle NonZero inclut tout région ≠ 0 :
    - Overlap solid+solid   : winding ≥ 2 → inclus (union correcte)
    - Trou circle_outline   : winding  0  → exclu (trou préservé)
    - Solid qui chevauche un trou : winding +1-1+1 = 1 → inclus (trou rempli, correct)

Chargement Clipper :
  loadClipper() injecte un <script> dans <head> au premier export.
  Si window.ClipperLib existe déjà, l'injection est ignorée.
  CDN : https://cdn.jsdelivr.net/npm/clipper-lib@6.4.2/clipper.js

Nouveaux composants dans export-otf.js :
  getCirclePolygon(cx, cy, r, n=32)
  getSquarePolygon(cx, cy, halfSize)
  getEllipsePolygon(cx, cy, rx, ry, n=32)
  getTraitPolygon(cx, cy, halfW, halfH, n=16)
  getCircleOutlinePolygons(cx, cy, outerR, innerR, n=32) → [outer, inner]
  loadClipper()
  unionPolygons(polygons)     → ClipperLib.Paths
  clipperToOpentypePath(paths) → opentype.Path

BUG — OTF REJETÉ PAR WINDOWS (08/04/2026)
------------------------------------------------------------

Symptôme :
  Les exports OTF ne s'ouvrent plus sous Windows (message d'erreur).
  Ils restent lisibles dans FontLab (plus permissif sur la structure).

Identifié à partir du commit : 65bf0dc — "ajout glyph export" (07/04 14:26)

Cause racine :
  Le fichier dinish-bold-metrics.json a été étendu à 138 glyphes dans ce
  commit (A–Z, a–z, chiffres, ponctuation + 84 caractères latins accentués :
  À Á Â Ã Ä Å Ç È É Ê Ë Ì Í Î Ï Ñ Ò Ó Ô Õ Ö Ù Ú Û Ü Ÿ
  et leurs équivalents minuscules : à á â ã ä å ç è é ê ë ì í î ï
  ñ ò ó ô õ ö ù ú û ü ÿ).

  Dans export-otf.js, le nom PostScript d'un glyphe est calculé par :
    const name = GLYPH_NAMES[char] || char;

  Or GLYPH_NAMES ne contenait aucun mapping pour les caractères accentués.
  Pour É (U+00C9) par exemple, le fallback donnait le caractère lui-même ('É')
  comme nom PostScript — un nom non-ASCII, invalide selon la spec PostScript.

  Les noms PostScript doivent être composés exclusivement de caractères ASCII
  (Adobe Glyph List). Un nom comme 'É' produit une table `post` malformée.
  Windows valide cette table strictement et rejette le fichier.
  FontLab tolère les noms non-conformes, d'où la divergence de comportement.

Fix appliqué (08/04/2026) :
  Ajout de 52 mappings dans GLYPH_NAMES (export-otf.js) selon l'Adobe Glyph
  List standard — tous les caractères accentués du JSON ont désormais un nom
  PostScript ASCII valide :
    'À':'Agrave',    'Á':'Aacute',      'Â':'Acircumflex', ...
    'à':'agrave',    'á':'aacute',      'â':'acircumflex', ...
    (liste complète dans export-otf.js, section GLYPH_NAMES)

  Note : le commentaire précédent "Letters and accented letters use the
  character itself as the PostScript name" était incorrect — c'est exactement
  ce comportement qui causait le bug.

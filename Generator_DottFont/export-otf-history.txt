ÉTAPE 3 — TENTATIVES DE CORRECTION DE BASELINE_Y
------------------------------------------------------------

Le problème central : trouver la position Y (en pixels canvas) du baseline
alphabétique quand le texte est rendu avec textBaseline='top' à y=PADDING.

renderTextMask() dessine ainsi :
  ctx.textBaseline = 'top';
  ctx.fillText(text, PADDING, PADDING);  // PADDING = 30px, FONT_SIZE = 150px

TENTATIVE A — fontBoundingBoxAscent avec textBaseline='alphabetic' (code initial)
  BASELINE_Y = PADDING + fontBoundingBoxAscent('H', textBaseline='alphabetic')
  Résultat : glyphes +211 unités au-dessus du baseline (BBox bottom = 211)
  Raison de l'échec : fontBoundingBoxAscent retourne l'ascender du font entier
  (~1050/1024 * 150 ≈ 153px), pas la distance entre le point 'top' et le baseline réel.

TENTATIVE B — alphabeticBaseline avec textBaseline='top'
  BASELINE_Y = PADDING + alphabeticBaseline('H', textBaseline='top')
  Résultat : glyphes décalés dans les valeurs négatives (en dessous du baseline)
  Testé sur Chrome ET Firefox avec le même résultat.
  Raison de l'échec : la spec Canvas utilise la convention "positif = vers le haut".
  Avec textBaseline='top', le baseline est EN DESSOUS du point de référence,
  donc alphabeticBaseline retourne une valeur NÉGATIVE dans Chrome/Firefox.
  → BASELINE_Y = PADDING + (valeur négative) = trop petit → glyphes trop bas.

TENTATIVE C — actualBoundingBoxDescent de 'A' avec textBaseline='top' (VALIDÉE)
  BASELINE_Y = PADDING + actualBoundingBoxDescent('A', textBaseline='top')
  Principe : 'A' a yMin=0 (touche exactement le baseline alphabétique).
  Sa descente depuis le point 'top' = distance de 'top' au baseline.
  actualBoundingBoxDescent est toujours positif (convention CSS, downward positive).
  → Valeur cross-browser stable.
  Résultat : CORRECT — alignement baseline validé

ÉTAPE 4 — TREMBLING (tremblement dans l'OTF exporté)
------------------------------------------------------------
Constaté : comparaison 04-07_test06 vs rendu navigateur → points perdent leur
alignement dans l'OTF, comme un tremblement colonne par colonne.

HYPOTHÈSE A — rounding flottant sur fx/fy (Math.round)
  Ajout de Math.round() sur fx et fy dans export-otf.js.
  Test07 : tremblement toujours présent → hypothèse incorrecte.

HYPOTHÈSE B — gradient normalisé à la largeur de chaque caractère (VALIDÉE)
  Cause racine : drawMeshGradientPreview() normalisait l'axe X du gradient
  sur canvasW (largeur variable par caractère). Chaque caractère avait donc
  une couleur de dot différente selon sa propre largeur → taille de dot variable
  colonne par colonne → apparence de "tremblement".

  Fix : ajout d'un paramètre refWidth à drawMeshGradientPreview().
  Lors de l'export OTF, on passe canvasH (constante = FONT_SIZE + 2*PADDING)
  comme référence fixe pour tous les caractères :
    drawMeshGradientPreview(canvasW, canvasH, undefined, canvasH)
  → le gradient est identique pour tous les caractères → dots cohérents.

  addTraitToPath(path, cx, cy, halfW, halfH)

  Ratios extraits des viewBox SVG en tenant compte de preserveAspectRatio="xMidYMid meet"
  sur un <use> carré → l'axe le plus court est contraint.

ÉTAPE 7 — EXPORT PNG
------------------------------------------------------------
Ajout d'un bouton PNG dans index.html + export-png-btn stylisé comme export-otf-btn.

Fonctionnement dans script-generator_DottFont.js :
  - Sérialise le SVG #output via XMLSerializer
  - Crée un Blob URL → charge dans un <img>
  - Dessine sur un <canvas> à résolution 4× (scale fixe)
  - Télécharge via canvas.toDataURL('image/png')
  Filename : {shape}_{tailleGen}_{size}_{presence}.png

Pourquoi SVG → canvas → PNG (et pas canvas direct) :
  L'output est un SVG (pas un canvas). SVG = vecteur → export SVG d'abord,
  puis rendu dans un canvas off-screen pour obtenir un bitmap haute résolution.
  Le facteur 4× est fixe pour garantir une qualité constante.

ÉTAPE 3 — TENTATIVES DE CORRECTION DE BASELINE_Y
------------------------------------------------------------

Le problème central : trouver la position Y (en pixels canvas) du baseline
alphabétique quand le texte est rendu avec textBaseline='top' à y=PADDING.

renderTextMask() dessine ainsi :
  ctx.textBaseline = 'top';
  ctx.fillText(text, PADDING, PADDING);  // PADDING = 30px, FONT_SIZE = 150px

TENTATIVE A — fontBoundingBoxAscent avec textBaseline='alphabetic' (code initial)
  BASELINE_Y = PADDING + fontBoundingBoxAscent('H', textBaseline='alphabetic')
  Résultat : glyphes +211 unités au-dessus du baseline (BBox bottom = 211)
  Raison de l'échec : fontBoundingBoxAscent retourne l'ascender du font entier
  (~1050/1024 * 150 ≈ 153px), pas la distance entre le point 'top' et le baseline réel.

TENTATIVE B — alphabeticBaseline avec textBaseline='top'
  BASELINE_Y = PADDING + alphabeticBaseline('H', textBaseline='top')
  Résultat : glyphes décalés dans les valeurs négatives (en dessous du baseline)
  Testé sur Chrome ET Firefox avec le même résultat.
  Raison de l'échec : la spec Canvas utilise la convention "positif = vers le haut".
  Avec textBaseline='top', le baseline est EN DESSOUS du point de référence,
  donc alphabeticBaseline retourne une valeur NÉGATIVE dans Chrome/Firefox.
  → BASELINE_Y = PADDING + (valeur négative) = trop petit → glyphes trop bas.

TENTATIVE C — actualBoundingBoxDescent de 'A' avec textBaseline='top' (VALIDÉE)
  BASELINE_Y = PADDING + actualBoundingBoxDescent('A', textBaseline='top')
  Principe : 'A' a yMin=0 (touche exactement le baseline alphabétique).
  Sa descente depuis le point 'top' = distance de 'top' au baseline.
  actualBoundingBoxDescent est toujours positif (convention CSS, downward positive).
  → Valeur cross-browser stable.
  Résultat : CORRECT — alignement baseline validé

ÉTAPE 10 — UNION BOOLÉENNE DES CONTOURS (Path > Union)
------------------------------------------------------------
Problème : chaque dot = 1 contour indépendant dans l'OTF.
Les contours se chevauchent, ce qui peut poser problème
dans certains renderers (PDF, imposition, logiciels de signe).

Objectif : fusionner tous les dots d'un glyphe en une seule
silhouette unifiée — équivalent de Path > Union dans Inkscape.

Solution : Clipper.js (port JS du moteur Clipper, union booléenne
de polygones), chargé dynamiquement depuis CDN sans modifier index.html.

Approche :
  - Les fonctions addXxxToPath (Bézier) sont remplacées par des
    fonctions getXxxPolygon retournant des tableaux de points {X, Y}
    (format Clipper, coordonnées en entiers via CLIPPER_SCALE = 100).
  - Les courbes sont approximées en polygones :
      circle        → 32 points (sub-pixel à toutes tailles)
      square        → 4 points (exact)
      ellipse       → 32 points
      trait         → 16 points par demi-cercle + segments droits
      circle_outline→ 32 points outer (CCW) + 32 points inner (CW = trou)
  - Après la boucle de génération, Clipper effectue l'union (ctUnion,
    pftNonZero) sur tous les polygones du glyphe.
  - Le résultat est converti en opentype.Path (moveTo / lineTo / close).

Winding :
  Toutes les formes solides sont générées en CCW (winding +1 en Y-up).
  Le polygone inner de circle_outline est généré en CW (winding -1)
  pour créer un trou. La règle NonZero inclut tout région ≠ 0 :
    - Overlap solid+solid   : winding ≥ 2 → inclus (union correcte)
    - Trou circle_outline   : winding  0  → exclu (trou préservé)
    - Solid qui chevauche un trou : winding +1-1+1 = 1 → inclus (trou rempli, correct)

Chargement Clipper :
  loadClipper() injecte un <script> dans <head> au premier export.
  Si window.ClipperLib existe déjà, l'injection est ignorée.
  CDN : https://cdn.jsdelivr.net/npm/clipper-lib@6.4.2/clipper.js

Nouveaux composants dans export-otf.js :
  getCirclePolygon(cx, cy, r, n=32)
  getSquarePolygon(cx, cy, halfSize)
  getEllipsePolygon(cx, cy, rx, ry, n=32)
  getTraitPolygon(cx, cy, halfW, halfH, n=16)
  getCircleOutlinePolygons(cx, cy, outerR, innerR, n=32) → [outer, inner]
  loadClipper()
  unionPolygons(polygons)     → ClipperLib.Paths
  clipperToOpentypePath(paths) → opentype.Path

BUG — OTF REJETÉ PAR WINDOWS (08/04/2026)
------------------------------------------------------------

Symptôme :
  Les exports OTF ne s'ouvrent plus sous Windows (message d'erreur).
  Ils restent lisibles dans FontLab (plus permissif sur la structure).

Identifié à partir du commit : 65bf0dc — "ajout glyph export" (07/04 14:26)

Cause racine :
  Le fichier dinish-bold-metrics.json a été étendu à 138 glyphes dans ce
  commit (A–Z, a–z, chiffres, ponctuation + 84 caractères latins accentués :
  À Á Â Ã Ä Å Ç È É Ê Ë Ì Í Î Ï Ñ Ò Ó Ô Õ Ö Ù Ú Û Ü Ÿ
  et leurs équivalents minuscules : à á â ã ä å ç è é ê ë ì í î ï
  ñ ò ó ô õ ö ù ú û ü ÿ).

  Dans export-otf.js, le nom PostScript d'un glyphe est calculé par :
    const name = GLYPH_NAMES[char] || char;

  Or GLYPH_NAMES ne contenait aucun mapping pour les caractères accentués.
  Pour É (U+00C9) par exemple, le fallback donnait le caractère lui-même ('É')
  comme nom PostScript — un nom non-ASCII, invalide selon la spec PostScript.

  Les noms PostScript doivent être composés exclusivement de caractères ASCII
  (Adobe Glyph List). Un nom comme 'É' produit une table `post` malformée.
  Windows valide cette table strictement et rejette le fichier.
  FontLab tolère les noms non-conformes, d'où la divergence de comportement.

Fix appliqué (08/04/2026) :
  Ajout de 52 mappings dans GLYPH_NAMES (export-otf.js) selon l'Adobe Glyph
  List standard — tous les caractères accentués du JSON ont désormais un nom
  PostScript ASCII valide :
    'À':'Agrave',    'Á':'Aacute',      'Â':'Acircumflex', ...
    'à':'agrave',    'á':'aacute',      'â':'acircumflex', ...
    (liste complète dans export-otf.js, section GLYPH_NAMES)

  Note : le commentaire précédent "Letters and accented letters use the
  character itself as the PostScript name" était incorrect — c'est exactement
  ce comportement qui causait le bug.

BUG — Paramètre Hazard ignoré à l'export OTF
  Problème : depuis l'ajout du slider Mesh (commit a98eda5, 10h52),
             script-generator_DottFont.js avait été mis à jour pour gérer
             meshSize=0 (brightness=0 partout → probabilité plate),
             mais export-otf.js utilisait toujours l'ancienne formule :
               probability = max(0, 1 - (brightness/204) * presenceStrength * 2)
             → quand meshSize=0, brightness=0 → probability=1 toujours
             → Hazard sans effet à l'export.
  Fix     : même logique que script-generator_DottFont.js :
               meshSize=0  → probability = 1 - presenceStrength
               meshSize>0  → max(0, 1 - (brightness/204) * presenceStrength * 2)

OPTIMISATION — Export OTF
  1. Courbes Bezier directes quand pas de chevauchement
       Quand 2 × MAX_RADIUS × sizeMultiplier ≤ DOT_SPACING,
       les dots ne se chevauchent pas → on bypass Clipper entièrement.
       Chaque forme est ajoutée directement comme courbe cubique Bezier
       (4 segments par cercle/ellipse, k=0.5523) dans l'opentype.Path.
       → Cercles lisses et précis dans le fichier OTF, pas de polygones.
       Quand chevauchement possible → Clipper union comme avant.

  2. Segments polygones réduits pour Clipper (n=32 → n=16)
       Moins de points pour Clipper union → ~2× plus rapide.
       Erreur visuelle < 0.4 font units, imperceptible.

  3. Skip du flou pendant l'export
       renderTextMask() créait un canvas flou complet si outsetRadius > 0.
       Le contour (offset) n'est pas exporté en OTF → travail inutile.
       Fix : outsetRadius sauvegardé et mis à 0 pendant la boucle glyphs.

  4. Indicateur de progression
       Le bouton OTF affiche "X / 138" et yield toutes les 10 glyphs
       (await setTimeout 0) → pas de freeze navigateur.

  5. Constantes hoistées hors de la boucle glyphs
       step, canOverlap, radiusMul, radiusBase, radiusRange calculés
       une fois avant la boucle au lieu de 138 fois.

  6. Fast path meshSize=0 pour le gradient
       Quand meshSize=0 le gradient est uniformément noir sur le texte,
       identique au masque texte. On lit ctx directement et on saute
       drawMeshGradientPreview() → économie de canvasW×canvasH×138 ops.

BUG — EXPORTS OTF INVISIBLES / IDENTIQUES DANS INKSCAPE
  Symptôme : plusieurs OTF installés sous Windows — visibles dans les
             paramètres polices de Windows, mais dans Inkscape les lettres
             ne changent pas visuellement selon la variante sélectionnée.

  Cause racine :
    nameID 16 (preferredFamily) était identique pour tous les exports :
    "FLUTGRABEN". Sur Windows, Inkscape utilise DirectWrite pour
    l'énumération des polices. DirectWrite groupe les fonts par nameID 16 :
    toutes les variantes apparaissaient donc comme une seule famille
    "FLUTGRABEN" dans le picker Inkscape. Windows font settings, lui,
    affiche par nom de fichier / nameID 1 — d'où la divergence observée.
    Inkscape prenait le premier (ou dernier) variant installé et ignorait
    les autres.

  Fix (10/04/2026) :
    Suppression des deux lignes suivantes dans export-otf.js :
      font.names.preferredFamily    = { en: 'FLUTGRABEN' };
      font.names.preferredSubfamily = { en: typographicStyle };

    Sans nameID 16/17, Inkscape retombe sur nameID 1 (legacyFamily),
    qui est déjà unique par export :
      ex. "FLUTGRABEN Ci M0 T1.00 S1.00 H0.50"
    → chaque export apparaît comme une famille distincte dans Inkscape.

  Trade-off :
    Figma et Adobe CC ne groupent plus les exports sous "FLUTGRABEN".
    Chaque export est une famille indépendante — comportement identique
    à nameID 1 seul. Acceptable pour un usage Inkscape-first.

  Note pratique :
    Désinstaller les anciens OTF et redémarrer Inkscape avant de tester
    (son cache font peut conserver les anciens noms).

PISTE — RÉDUCTION DU POIDS OTF (objectif : 200 Ko)
------------------------------------------------------------
Non implémenté. À étudier selon l'usage.

Contexte : la taille d'un OTF généré vient presque entièrement du nombre
de points par glyphe (courbes CFF). Avec 138 glyphes et des dizaines à
des centaines de dots par lettre, les exports peuvent dépasser 200 Ko.

Leviers identifiés (du plus au moins impactant) :

  1. SUBSET À L'EXPORT
       Ajouter une option "quels glyphes exporter" (ex. A–Z = 26 glyphes,
       A–Z + a–z = 52, complet = 138).
       Gain linéaire : A–Z seulement → taille ÷ ~5.
       Aucune dégradation de qualité — l'utilisateur choisit ce dont il a besoin.

  2. BYPASS CLIPPER (forcer le mode Bezier)
       En mode overlap, Clipper crée des polygones N=16 points par dot
       (~150 bytes/cercle en CFF). Le mode Bezier (4 segments cubiques)
       produit ~30 bytes/cercle.
       Gain potentiel : ÷ 4 à ÷ 5 sur les glyphes en mode overlap.
       Impact visuel : nul à l'écran et en impression standard. La différence
       n'existe que dans des contextes très spécifiques (transparence PDF,
       imposition, certains RIP). À proposer comme flag "export léger".

  3. RÉDUIRE N DES POLYGONES CLIPPER (N=16 → N=8)
       ÷ 2 sur les points en mode overlap.
       Erreur visuelle < 1 font unit à ces tailles, imperceptible.

  Pour atteindre 200 Ko avec 138 glyphes complexes : combiner 1 + 2, ou
  appliquer 1 seul avec un subset strict (A–Z).

  Contexte : l'union Clipper.js fonctionne mais présente des limitations
             connues qui méritent d'être documentées pour une future évolution.

  Contenu :
    - Pourquoi l'union est obligatoire dans un fichier OTF
        (contours superposés → trous visuels selon fill rule, rejet par outils)
    - Solution actuelle : union côté client avec Clipper.js
        fonctionnement : polygonisation → ClipperLib ctUnion pftNonZero
        → clipperToOpentypePath → opentype.js

        renvoie le binaire au navigateur.

BUG — APPROCHES LATÉRALES DÉCALÉES À L'EXPORT OTF AVEC TRACKING
  Symptôme : les valeurs LSB/RSB visibles dans FontLab ne correspondaient
             pas aux zones d'approches affichées dans l'overlay web
             (checkbox "approches" du panneau avancé).
             Exemple observé sur 'l' avec tracking > 0 :
               overlay web  → LSB ≈ 168 u
               FontLab OTF  → LSB = −31 u  (écart ~200 unités)

  Cause racine :
    Le monkey-patch ctx.fillText (reglage_advance.js) dessine chaque
    caractère à (PADDING + extraLsb) sur le canvas — le corps du glyphe
    est décalé à droite proportionnellement à son ratio LSB/RSB d'origine.

    Dans export-otf.js, la conversion canvas px → font units soustrayait
    ce même extraLsb :
      fontX = (x − PADDING − extraLsb) × SCALE
    Ce faisant, le décalage était annulé, plaçant le glyphe à son LSB
    DINish original dans l'OTF — sans tenir compte du tracking gauche.
    Parallèlement, tout le tracking allait au RSB (via advanceWidth élargi),
    créant une distribution 0/100 au lieu de la distribution proportionnelle
    montrée dans l'overlay.

  Fix appliqué (export-otf.js) :
    1. Suppression du bloc de calcul extraLsb (lignes ~406–428) :
         let extraLsb = 0; if (letterSpacingPx !== 0 && dinishFont) { ... }
       Ce calcul était inutile puisque la valeur n'est plus utilisée.

    2. Correction de la formule fontX :
         Avant : fontX = Math.round((x − PADDING − extraLsb) × SCALE)
         Après : fontX = Math.round((x − PADDING) × SCALE)
       Le canvas contient déjà le décalage proportionnel : en ne le
       soustrayant plus, l'OTF reflète le même LSB que l'overlay web.

  Résultat :
    OTF LSB = original_lsb + extraLsb_units  (= valeur overlay)
    OTF RSB = original_rsb + extraRsb_units  (= valeur overlay)
    advanceWidth = original + tracking total  (inchangé)

  Note : un LSB négatif dans FontLab avec size > ~2.0 et shapes anguleuses
  (cross, polygone) reste attendu et correct — les formes débordent
  physiquement du bounding box de la lettre vers la gauche.

EXPORT WOFF
  Objectif : générer un fichier .woff depuis le même pipeline que l'OTF,
             sans dépendance externe.

  Architecture :
    buildFont(progressBtn) — extrait de l'ancienne exportOTF().
      Contient tout le pipeline (Clipper, métriques, glyphes, patch OS/2 + post).
      Retourne { buffer: ArrayBuffer, filename } ou null sur erreur.
      progressBtn.textContent mis à jour avec la progression ("42 / 250").

    exportOTF() — wrapper mince : appelle buildFont, télécharge en .otf.
    exportWOFF() — wrapper mince : appelle buildFont, convertit via sfntToWoff(),
      télécharge en .woff.

  deflateCompress(data) :
    Compression zlib (RFC 1950) via CompressionStream('deflate') natif navigateur.
    Retourne Promise<Uint8Array>.

  sfntToWoff(sfntBuffer) :
    Lit la structure sfnt (header 12 octets + records 16 octets × numTables).
    Compresse chaque table individuellement ; garde la version non compressée
      si elle est plus petite.
    Construit le fichier WOFF :
      Header 44 octets (signature 'wOFF', flavor, totalSize, numTables,
        totalSfntSize, version, meta/priv à zéro).
      Table directory : 20 octets × numTables (tag, offset, compLength,
        origLength, origChecksum).
      Données tables compressées, chacune paddée à 4 octets.
    Retourne Promise<ArrayBuffer>.

  index.html : bouton #export-woff-btn ajouté à côté de OTF.
  CSS : #export-woff-btn ajouté aux règles de style et hover des boutons export,
        caché en mode image (.mode-image).

  Bug corrigé : la progression "gi / total" s'affichait sur le bouton OTF même
    lors d'un export WOFF — exportOtfBtn.textContent → progressBtn.textContent.

BUG — POST TABLE : underlinePosition=0, underlineThickness=0
  Symptôme : les exports OTF et WOFF avaient underlinePosition=0 et
             underlineThickness=0 dans la table post.
             Le soulignement CSS s'affichait sur la baseline au lieu

  Analyse préalable (issue.txt du 05/05) :
    Le fichier issue.txt présent dans correction-otf/05-05/ contenait
    une analyse incorrecte des WOFF — il confondait origLen (taille
    non compressée) avec compLen (taille compressée), et signalait à
    tort une corruption du table directory.
    Vérification binaire + fonttools : les 4 fichiers WOFF sont
    structurellement valides, toutes les tables se décompressent
    correctement, aucune corruption réelle.

  Cause racine du bug underline :
    Le bloc de patch post-sérialisation dans buildFont() assignait :
      patchedFont.tables.post.underlinePosition  = -153
      patchedFont.tables.post.underlineThickness = 51
    opentype.js v1.3.4 recopie les bytes bruts mis en cache lors du
    parse() dans toArrayBuffer(), sans re-sérialiser les champs JS
    modifiés. L'assignation était silencieusement ignorée.
    (Le patch OS/2 fonctionne car opentype.js re-génère cette table
    explicitement ; le patch post ne fonctionnait pas pour la même
    raison inverse.)
    Ce bug affectait les deux formats d'export (OTF et WOFF) puisqu'ils
    partagent le même buildFont().

  Fix appliqué (export-otf.js) :
    Suppression du bloc d'assignation JS sur patchedFont.tables.post.
    Remplacement par un patch binaire direct après toArrayBuffer() :
      1. Parcourir le répertoire sfnt (12 + t*16 par table)
      2. Localiser l'entrée tag='post'
      3. Lire l'offset de la table dans le buffer
      4. setInt16(postOff + 8,  -153)   underlinePosition
         setInt16(postOff + 10,   51)   underlineThickness
      5. Recalculer le checksum de la table post (somme des uint32
         big-endian, mod 2^32) et l'écrire dans le répertoire sfnt.

  Résultat :
    post.underlinePosition  = -153 ✓
    post.underlineThickness =   51 ✓
    Checksum post = 0xFF6A0033 (recalculé) ✓

  Objectif : que les exports OTF et WOFF reflètent correctement la
             variante DINish Bold Italic quand la checkbox adv-italique
             est cochée — métadonnées, tables binaires, et métriques
             issues du bon fichier de référence.

  Nouveau fichier — source_export_otf/dinish-bold-italic-metrics.json :
    Même structure que dinish-bold-metrics.json.
    Extrait depuis DINish-BoldItalic.woff via fontTools (Python).
    482 glyphes — advance widths identiques au Bold (confirmé sur les
    548 glyphes partagés), mais bbox différentes : les letterforms
    penchées font déborder l'encre au-delà de l'advance box
    (ex. 'A' : xMin Bold=4 → xMin Italic=-51).
    ascender corrigé à 1024 (même logique que session 27/04 sur le Bold :
    sTypoAscender DINish = UPM, pas usWinAscent=1050).

  buildFont() — export-otf.js :
    isItalic déclaré en tête de fonction (lu une seule fois depuis
    #adv-italique, utilisé dans tout buildFont()).

    Sélection du fichier de métriques :
      isItalic = false → dinish-bold-metrics.json  (inchangé)
      isItalic = true  → dinish-bold-italic-metrics.json  (nouveau)

    Métadonnées opentype.Font :
      styleName      : 'Regular' | 'Italic'  (nameID 2)
      legacyFamily   : suffixe ' I' ajouté si italic
                       ex. "FLTGRRR Ci M0 T1.00 S1.00 H0.50 I"
      typographicStyle : préfixe 'Italic ' si italic
      description    : idem (champ description dynamique)

    Filename OTF/WOFF :
      FLTGRRR_I_{shape}_... si italic
      FLTGRRR_{shape}_...   si non-italic

    Patches binaires étendus (même boucle sfnt que la table post) :
      post  : italicAngle patché en Fixed 16.16
                italic → -12 * 65536 (= 0xFFF40000, ref DINish Bold Italic)
                non-italic → 0
      head  : macStyle (uint16 à offset+44)
                italic → 3 (Bold + Italic)
                non-italic → 1 (Bold)
      OS/2  : fsSelection patché via propriété JS (avant 2e toArrayBuffer)
                italic → 161 (0b10100001 : Bold + Italic bit)
                non-italic → 160 (0b10100000 : Bold bit)
      Checksums recalculés via recomputeTableChecksum() (nouvelle
      fonction helper factorisée depuis le patch post existant).

  Boucle sfnt refactorisée :
    Avant : boucle for + break au premier 'post' trouvé.
    Après : boucle for sans break, gère 'post' et 'head' dans la même
    passe. recomputeTableChecksum(recOffset, tableOff, tableLen) extrait
    le calcul de checksum répété.

  BUG — TRACKING ITALIC (identifié, non encore corrigé)
    Deux problèmes détectés lors de l'analyse du pipeline italic :

    1. BASELINE_Y mesuré en Bold dans buildFont()
       export-otf.js ligne ~428 : ctx.font est fixé à '700 150px DINish'
       (Bold) avant de mesurer actualBoundingBoxDescent('A'), même quand
       isItalic=true. Si la mesure diffère entre Bold et Bold Italic,
       la conversion canvas px → font units Y est décalée pour tout
       le glyphe italic.
       Fix prévu : préfixer 'italic ' dans ctx.font si isItalic.

    2. extraLsb négatif pour les glyphes italic à LSB négatif
       Le monkey-patch ctx.fillText (reglage_advance.js) distribue le
       tracking proportionnellement : extraLsb = spacing × (lsb / total).
       Pour les glyphes italic avec LSB < 0 (ex. 'A' italic : lsb=-51,
       rsb=59, total=8), extraLsb devient très négatif (≈ -63px pour
       spacing=10px) → le glyphe est projeté loin à gauche.
       Fix prévu : Math.max(0, lsbPx) et Math.max(0, rsbPx) avant le
       calcul du ratio ; fallback à spacing/2 si total ≤ 0.

CORRECTIONS APPLIQUÉES (19/07/2026)
------------------------------------------------------------

  BUG 1 — BASELINE_Y mesuré en Bold pour l'italic (export-otf.js ~428)
    Symptôme : la mesure actualBoundingBoxDescent('A') utilisait toujours
    ctx.font = '700 150px DINish' (Bold), même en mode italic → décalage Y
    de la conversion canvas px → font units pour tous les glyphes italics.
    Fix : préfixe 'italic ' ajouté si isItalic=true :
      ctx.font = `${isItalic ? 'italic ' : ''}700 ${FONT_SIZE}px DINish, sans-serif`;

  BUG 2 — extraLsb négatif pour les glyphes italic à LSB négatif
    (reglage_advance.js — 3 emplacements)
    Symptôme : le monkey-patch ctx.fillText distribue le tracking selon le
    ratio lsb/(lsb+rsb). Pour les glyphes italics avec LSB<0 (ex. 'A' italic :
    lsb=-51, rsb=59, total=8), extraLsb devenait très négatif (≈-63px pour
    spacing=10px) → projection du glyphe loin à gauche.
    Fix : Math.max(0, lsbPx) et Math.max(0, rsbPx) avant le calcul du ratio
    dans les trois emplacements (computeGlyphPositions, sidebar display,
    fillText monkey-patch). Pour 'A' italic : extraLsb passe de -63px à 0.

  BUG 3 — Centrage forcé LSB=RSB cassant l'espacement italic (export-otf.js ~752)
    Symptôme : l'algorithme de centrage forçait LSB=RSB pour tous les glyphes,
    y compris en mode italic. Pour 'j' italic (inkWidth=400, advW=246 UPM),
    le centrage donnait LSB=RSB=-77, soit 45 unités de débordement droit de
    plus que le -32 prévu par DINish Italic → 'j' et 'u' se touchaient
    visuellement dans l'export OTF alors que le générateur était correct.
    Cause racine : DINish italic a des sidebearings intentionnellement
    asymétriques pour compenser l'angle de l'italique (-12°). Le centrage
    symétrique détruit cette logique.
    Fix : condition !isItalic ajoutée autour du bloc de centrage :
      if (!isItalic && path.commands.length > 0) { ... }
    En mode italic, les sidebearings DINish Italic bruts sont conservés tels
    quels, reflétant fidèlement l'espacement prévu par la fonte source.

  NOTE — Affichage FontLab vs générateur
    L'écart observé (ex. 'A' : générateur 0/59, export lu dans FontLab 75/-70)
    s'explique par trois couches distinctes :
    1. Le générateur affiche les métriques de la fonte source DINish (template).
    2. L'OTF exporté contient les métriques FLTGRRR recalculées (dots + centrage).
    3. FontLab ajuste l'affichage LSB/RSB selon l'angle italic (-12°) en
       projetant les points de contour sur l'axe oblique → valeurs visuelles
       différentes des coordonnées brutes. Ce comportement est normal et attendu.
    Debug vérifié : console log après opentype.parse() confirmait
    xMin=3 xMax=616 advW=620 pour 'A', soit LSB≈3 RSB≈4 en coordonnées brutes.
